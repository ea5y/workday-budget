## 0. 摘要

把「今天的工作」当成一笔**有硬上限的预算**来经营：花完就收工，干完也收工。省下的时间强制转投到自己的事业上；没干完的部分顺延，**这不是个人的债，是排期的问题**。

三条核心公式：

```
交付日期   = 范围 ÷ 日预算          ← 日期是算出来的结果，不是拍出来的承诺
今日收工   = min(预算用尽, 交付完成)  ← 两种结局都算正常收工，只是结算不同
今日收益   = 标准工作日 − 实际墙钟    ← 真正的产出是"多出来的半天"
```

四个环：

1. **计量环**：AI 编程的消耗折算成钱，逐日累计，可审计；
2. **硬顶环**：到 100% 立即停，只剩收尾动作；继续工作唯一合法通道是**二级上限**；
3. **排期环**：范围与预算决定日期；算出来晚于期望就摆出三个杠杆，而不是加班；
4. **再投资环**：收工即开启个人时间块，并单独记账。

一句话价值：**让时间有价格，让结余有去处，让延期有据可查。**

## 1. 背景与问题

### 1.1 三个场景

| # | 场景 | 用户原话（意译） |
|---|---|---|
| S1 | AI 编程限额 | 一天用在 AI 编程上的钱最多 10 块，超过必须停止；上限可配；**即使没干完也停** |
| S2 | AI 资讯 | 每天要知道有没有大事，尤其 Codex / Claude Code / DeepSeek / CC Switch；关注对象可指定 |
| S3 | 时间再投资 | 半天干完就算一天干完，省下的半天投给自己的自媒体 |

### 1.2 共同结构

三个场景结构一致：**给一类稀缺资源划边界，再把省下的容量转投到别处。**

| 场景 | 被约束的资源 | 边界 | 释放出的容量 | 去向 |
|---|---|---|---|---|
| S1 | AI 编程消耗（钱） | 日预算 10 元，硬性 | 未花完的额度 | 兑换成时间 |
| S2 | 信息焦虑（注意力） | 每天 2 分钟 | 漫无目的刷资讯的时间 | 回到工作或个人 |
| S3 | 工作时长 | 预算用尽或交付完成 | 半天时间 | 个人事业 |

### 1.3 真正要解决的问题

不是"省钱"，也不是"看新闻"。是：**一天的时间没有标价，所以会被无意识地稀释**——上班时用加班兜底，下班后用刷手机兜底。

用户要的是一套**外部约束装置**，并且明确了一件事：**溢出的时间成本由公司承担，不由个人吸收**。这意味着产品不是"自律打卡器"，而是**边界工具 + 证据生成器**：它负责准时关门，并负责把"为什么没做完"变成一份可以拿出去的客观记录。

> 产品本质：一份和自己签的**注意力合同**，外加一份给公司的**排期对账单**。

## 2. 产品定位

**是什么**：本地优先的个人工具，装在 AI 编程宿主里，管一天的"工作预算""交付排期"和"个人时间"。

**不是什么**：不是团队效能工具，不是老板看板，不是通用时间追踪器，不是模型路由器，不是加班助手。

**成功的样子**：连续使用 4 周，周报能看到"本周为公司 22 小时 / 为自己 18 小时"，个人账号有可见产出，且至少有一次用溢出报告推动了范围或日期的调整。

## 3. 设计原则

| # | 原则 | 含义 | 反面案例 |
|---|---|---|---|
| P1 | **预算即硬顶** | 到 100% 立刻收工，没干完也停；未完成顺延，不许"再来一会儿" | "就差一点，今天破个例" |
| P2 | **溢出归排期，不归人品** | 没干完不等于不努力；记录为排期偏差，推动改范围或改日期 | 自责 → 偷偷加班 → 规则失效 |
| P3 | **日期是算出来的** | 先定预算与范围，日期是结果；想要更早的日期，只能动预算或范围 | 先答应一个日期，再倒推加班 |
| P4 | **紧急通道必须昂贵且受限** | 二级上限有前置条件、次数配额、事后统计，否则它就是新的默认上限 | 每天都能"临时开一下" |
| P5 | **计量必须经得起自欺** | 数字来自日志与账单，不来自手动填写 | 手动"今天大概花了 8 块" |
| P6 | **空报告是合法输出** | 没有大事就明确说没有，不凑数 | 每天硬凑 10 条"值得关注" |
| P7 | **本地优先，没有老板视图** | 数据不出本机，不做排名与考核 | 一旦感觉被监控，用户就开始骗系统 |
| P8 | **收益框架优先** | 主视觉是"今天还剩多少自由时间"，不是"你花了多少钱" | 每天一个红色超支数字 → 焦虑 → 弃用 |

## 4. 核心概念

| 术语 | 定义 |
|---|---|
| **日预算** | 默认 10 元。**硬性**：达到即收工，与交付是否完成无关 |
| **二级上限** | 默认 20 元，默认关闭。仅在"赶交付"场景显式启用，有配额 |
| **元当量** | 把所有计费方式（按量 / 订阅 / 赠送额度）折算成人民币等值，用于和预算比较 |
| **时间当量** | 元 → 小时的换算率，默认 1 元 = 48 分钟（即 10 元 ≈ 8 小时），可配 |
| **交付项** | 一条"今天必须产出什么"，含完成定义、预估成本、承诺日期 |
| **顺延（Carry）** | 未完成项移到次日待办队首，优先于新任务 |
| **溢出（Spill）** | 预算用尽但交付未完成。记录为排期偏差，不是个人过失 |
| **溢出报告** | 自动生成的客观记录：预算、已花、完成项、顺延项、预测日期 vs 承诺日期 |
| **排期（Schedule）** | 由"范围 ÷ 预算"推算的 P50 / P80 交付日，与期望日期比对 |
| **收尾豁免** | LOCKED 后仍允许提交/测试/写交接的独立小额额度（默认 0.5 元） |
| **双账本** | 公司账本（有硬顶）+ 自己账本（有下限、受保护） |
| **个人时间块** | 收工后开启的受保护时段，必须绑定一个产出物 |

## 5. 两个剧本

### 5.1 顺利的一天

| 时间 | 事件 | 系统行为 |
|---|---|---|
| 08:25 | 晨报 | 2 分钟简报；不计入工作预算 |
| 08:40 | 开工 | 登记 1–3 条交付项 + 预估；预算 10 元 |
| 11:30 | 预算到 70% | 提示剩余额度与未完成项，建议砍范围 |
| 12:10 | 交付全部勾选，已花 4.2 元 | DONE："今天结束了，你为自己争取了 5 小时 50 分" |
| 12:15 | 开启个人时间块 | 锁定 4 小时，填写今日产出物 |
| 18:00 | 日报 | 花了多少 / 交付了什么 / 省下多少 / 明天第一件事 |

### 5.2 用尽的一天（关键路径）

| 时间 | 事件 | 系统行为 |
|---|---|---|
| 09:00 | 开工 | 3 条交付项，预估合计 14 元 → 系统提示"预估超出日预算，可能顺延 1 项" |
| 15:40 | 预算到 90% | WINDDOWN：不再开新任务，只允许修补 |
| 16:20 | 预算到 100% | **LOCKED**：公司账本关闭，只剩收尾豁免额度 |
| 16:25 | 收尾 | 提交、跑测试、写交接摘要，消耗 0.3 元（豁免额度内） |
| 16:35 | 自动结算 | 生成溢出报告：完成 2/3，顺延 1 项，预测交付日 11-06，承诺日 11-05 |
| 16:40 | 收工 | 主界面不再显示"还能干多久"，只显示"明天第一件事"和"今天到这里" |

> 设计要点：LOCKED 之后**界面上不存在"继续对话"的入口**，只有"申请二级上限"（条件不满足时置灰并说明原因）。

## 6. 功能需求

优先级：P0 = 没有它产品不成立；P1 = 首个可用版本；P2 = 后续增强。

### FR-1 计量与归集（P0）

- **FR-1.1** 读取宿主会话数据，按请求累计 token：`input`、`cache_read`、`cache_write`、`output`。
- **FR-1.2** 本地价格表按模型分四档计价，支持生效日期版本化；缓存命中价与未命中价必须分开（两者可差一个数量级）。
- **FR-1.3** 归集粒度：请求级事件 → 会话 → 日账；支持按会话/项目打标签。
- **FR-1.4** 去重：同一请求同时被会话日志与代理捕获时按 request id 合并。
- **FR-1.5** 对账：月度与厂商账单比对，偏差 > 5% 提示"价格表可能过期"。
- **FR-1.6** 口径声明：宿主提供的成本字段为**估算值**，一律以本地价格表重算为准，两套数字都保留以便审计。
- **FR-1.7**（P1）接入非宿主工具：解析 Claude Code / Codex 本地会话日志；或经本地代理统一记账。

> 技术风险：宿主是否暴露逐请求用量与 request id，需 M0 验证。若只有会话级汇总，降级为"会话级估算 + 按轮次比例分配"，UI 标注精度。

### FR-2 硬上限与二级上限（P0）

**硬上限**

- **FR-2.1** 日预算默认 10 元，可配置；工作日 / 周末可不同；改当天预算需二次确认并记入变更日志。
- **FR-2.2** 达到预算 100% 时：立即进入 `LOCKED`，**禁止任何新任务**，无论交付是否完成。
- **FR-2.3** 收尾豁免：LOCKED 后仍可提交、跑测试、写交接摘要，独立额度默认 0.5 元；额度用尽后只允许零 token 的本地操作（git commit、打包、归档）。
- **FR-2.4** 状态机：`NORMAL(0–70%) → WARN(70–90%) → WINDDOWN(90–100%) → LOCKED(100%)`。
- **FR-2.5** 预算分池（P1，可关）：生产 8 元 + 探索 2 元。探索池用于"想不清楚先试"的高消耗探索，月底清零。
- **FR-2.6** **不借贷、不预支**：今日额度不可从明日借用，也不可从明日提前消耗。

**二级上限**

- **FR-2.7** 默认 20 元，默认关闭。启用后当日上限切换为 20 元，状态机在 18 元处告警、20 元处锁定。
- **FR-2.8** 启用前置条件（至少满足其一，否则入口置灰并显示原因）：
  - 距**承诺交付日** ≤ 2 天，且剩余工作量 > 1 个标准日；
  - 交付方书面要求提前交付（需粘贴一句原文）。
- **FR-2.9** 启用动作需：二次确认 + 填写一句理由 + 选择释放的天数（1 天 / 连续 N 天）；全部记入账本。
- **FR-2.10** 配额：每月最多 4 次（可配）；当月第 3 次起，启用前必须展示"本月已启用 X 次，排期可能偏乐观"。
- **FR-2.11** 二级上限用尽仍未完成 → 记为 `SPILL_HARD`，这是排期失效的**最强证据**，写入溢出报告首行。
- **FR-2.12** 周报统计：本月启用次数、因启用而避免的延期天数、启用后仍溢出的次数。

### FR-3 排期与交付日期（P0）

- **FR-3.1** 任务录入：标题、完成定义、预估成本（元）、依赖、期望交付日、优先级。
- **FR-3.2** 排期计算：按日预算与近 4 周实际吞吐（日均花费、完成率、预估偏差）推算 `P50 完成日` 与 `P80 完成日`。
- **FR-3.3** 若 `P80 > 期望交付日`，标记"不可行"，并给出三个杠杆（必须三选一或组合）：
  1. **加预算**：启用二级上限 / 临时提高日预算；
  2. **减范围**：列出可延后的项，显示砍掉后新的日期；
  3. **改日期**：给出建议日期（P50 与 P80 两个选项）。
- **FR-3.4** 承诺日由用户确认后锁定；变更需记录"谁改的、为什么、对预算的影响"。
- **FR-3.5** 每日收工时更新预测；一旦 `预测日 > 承诺日`，**当天就预警**，不等到期才发现。
- **FR-3.6** 预估偏差学习：对比 `est_cost` 与 `actual_cost`，滚动给出"你的预估通常偏低 30%"这类提示。

### FR-4 交付闸门与顺延（P0）

- **FR-4.1** 开工前登记 1–3 条交付项；每条必须有可验证的完成定义。
- **FR-4.2** `DONE` 条件：全部交付项完成 ∧ 已花 ≤ 预算（含豁免额度）。
- **FR-4.3** 未完成项自动顺延到次日**队首**，优先于新任务安排。
- **FR-4.4** 积压闸门：当顺延工作量 > 2 个标准日时，开工前强制弹出"重谈"对话（范围 / 日期 / 预算三选一）；未处理则每天重复提示。
- **FR-4.5** 顺延只记录为排期偏差，不扣分、不显示"连续失败天数"（避免羞辱式设计）。

### FR-5 溢出报告（P0）

- **FR-5.1** 每次 `SPILL` / `SPILL_HARD` 自动生成一条记录：日期、预算、实际花费、完成项、顺延项、预测交付日、承诺交付日、是否启用二级上限。
- **FR-5.2** 一键生成"对外三句话"（模板可配）：当前资源下的实际进度、按此速度的预计交付日、需要调整的一项（范围或日期）。
- **FR-5.3** 报告可导出 Markdown / 复制到剪贴板，便于贴进周报或聊天窗口。
- **FR-5.4** 周报汇总：本周溢出天数、累计延迟天数、二级上限启用次数、因调整而追回的进度。
- **FR-5.5** 文案基调必须是**陈述而非申诉**：只给数据和建议，不带情绪、不指责排期方。

> 这是"时间成本归公司"能够成立的前提。没有书面日期与可见记录，延期会默认算在个人头上。

### FR-6 结余与再投资（P0）

- **FR-6.1** **结余不结转成额度**（避免攒额度后报复性使用，破坏硬顶）。结余只兑换为时间。
- **FR-6.2** 按时间当量折算：`结余时间 = (预算 − 实际花费) × 时间当量`，默认 1 元 = 48 分钟。
- **FR-6.3** 同时记录**墙钟**：开工 / 收工时间；`今日收益 = 标准工作日时长 − 实际墙钟`。
- **FR-6.4** `DONE` 时展示"今日为自己争取 X 小时 Y 分"，主按钮为"开启个人时间块"。
- **FR-6.5** 个人时间块默认 4 小时，可调；导出 ICS 写入日历；开始前 5 分钟提醒。
- **FR-6.6** 自己账本：记录时间块 + 产出物（文章 / 视频脚本 / 代码 / 其他），产出物不必发布但必须存在。
- **FR-6.7** 防蒸发：时间块开始后 15 分钟未启动标记"未使用"；连续 3 天未使用给出提示。
- **FR-6.8** 周视图：公司 vs 自己 的时间与金额对比，以及"本周多出几个半天"。

### FR-7 资讯简报（P1）

- **FR-7.1** 关注对象可配：默认 DeepSeek、OpenAI Codex、Claude Code、CC Switch；可加任意 GitHub 仓库 / RSS / 站点。
- **FR-7.2** 来源优先级：官方 changelog 与 release notes > GitHub Releases > 官方博客 > HN / X > 中文媒体。
- **FR-7.3** 分级：`P0 必须知道`（模型发布、价格与计费变更、破坏性变更、安全通告、关注仓库的 major release）/ `P1 值得知道` / 噪音丢弃。
- **FR-7.4** 长度硬约束：≤ 5 条、≤ 300 字、≤ 2 分钟；每条必须有一句"**这跟你有什么关系**"。
- **FR-7.5** 空报告合法：无 P0 事件时输出"今天没有值得你花时间的事"，条数为 0，不产生通知。
- **FR-7.6** 推送：每日固定一次（默认 08:30）+ P0 即时告警（每小时聚合，每天最多 1 条）。
- **FR-7.7** 去重：同一事件多源出现时按事件聚类，只保留一条并附多源链接。
- **FR-7.8** 资讯时间不计入工作预算，计入自己账本（认知投资）。

### FR-8 面板与复盘（P1）

- **FR-8.1** 主面板：今日剩余自由时间（大）、已用预算（小）、交付项进度、预算状态、距承诺日天数。
- **FR-8.2** 日报：已花 / 交付 / 结余 / 顺延 / 明日第一件事。
- **FR-8.3** 周报：预算达成率、溢出天数、二级上限启用次数、自己账本时长、资讯命中率。
- **FR-8.4** 导出：CSV / JSON / Markdown 周报。

### FR-9 配置与扩展（P2）

- **FR-9.1** 配置项：日预算、二级上限、启用配额、时间当量、收尾豁免额度、分池比例、资讯源、简报时间、个人块默认时长。
- **FR-9.2** 价格表手动更新 + 可选在线更新（默认关闭）。
- **FR-9.3** 对外提供只读数据接口，便于将来做移动端或自建看板。

## 7. 状态机

### 7.1 预算状态

| 状态 | 触发 | 允许的动作 | 系统提示 |
|---|---|---|---|
| `NORMAL` | 已花 < 70% | 全部 | 无 |
| `WARN` | 70%–90% | 全部，新任务需确认预估 | "还剩 X 元，建议先砍范围" |
| `WINDDOWN` | 90%–100% | 仅收尾与已开任务的修补 | "进入收尾，不再开新任务" |
| `LOCKED` | ≥ 100%（未启用二级） | 仅收尾（豁免额度 0.5 元）+ "申请二级上限"入口 | "今天的额度用完了，到这里" |
| `TIER2` | 已启用二级，10%–90% | 全部 | "二级上限已启用，剩余 X 元" |
| `TIER2_WARN` | 二级下 ≥ 90% | 仅收尾与修补 | "二级上限快用完了" |
| `TIER2_LOCKED` | 二级下 ≥ 100% | 仅收尾 | "二级上限也用完了" |
| `DONE` | 交付全完成 ∧ ≤ 预算 | 收工，开启个人时间 | "今天结束了，你为自己争取了 X" |
| `SPILL` | 预算用尽 ∧ 未完成 | 收工，生成溢出报告 | "没做完的部分顺延到明天" |
| `SPILL_HARD` | 二级上限用尽 ∧ 未完成 | 收工，生成强证据报告 | "已动用二级上限仍未完成" |

### 7.2 预算 × 交付

| 预算 \ 交付 | 未完成 | 全部完成 |
|---|---|---|
| < 上限 | 继续工作 | **DONE**：收工，收益入账 |
| ≥ 上限 | **SPILL**：收工 + 溢出报告 + 顺延 | 收工，收益为 0（用满了一天） |

**两种收工都是正常收工**，区别只在结算方式——这是价值观，也是防止"没干完就内疚"的设计。

## 10. 边界与非目标

- ❌ 不做团队版、管理者视图、排行榜
- ❌ 不记录窗口标题、键鼠活动、屏幕内容
- ❌ 不做模型路由 / 自动选便宜模型（会让计量失去意义）
- ❌ 不做"道德记账"：不统计加班时长、不鼓励延长工时、不提供"再干一小时"的按钮
- ❌ 不强制发布自媒体内容，只保证时间被用在产出物上
- ❌ 不用积分、徽章、连续打卡等游戏化手段（会诱导为分数而伪造行为）

关于"溢出"的边界，需写进产品说明：**系统永远不建议"多干一会儿"**。它只会建议加预算、减范围、改日期——而且加预算这件事，默认要动二级上限，要理由，要配额。

## 11. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **顺延积压螺旋** | 每天顺延 1 项，一周后欠 5 项，规则悄悄失效（开始"预支明天"） | 积压闸门（> 2 标准日强制重谈）、每日更新预测、到期前预警而非到期才发现 |
| **二级上限滑坡** | "今天有点赶" → 天天启用 → 20 元变默认 | 前置条件 + 每月配额 + 启用统计 + 第 3 次起强制提示；入口在条件不满足时置灰 |
| **硬停留半成品** | 停在工作树中间，第二天恢复成本高 | 收尾豁免额度、自动生成交接摘要、禁止硬杀进程 |
| 成本估算失真 | 与账单偏差大，用户不信任数字 | 双轨记录（估算/账单）、月度对账、超阈值告警 |
| 混合计费击穿口径 | 订阅制边际成本≈0，"10 元"无对应物 | 元当量 + 影子价格（订阅费 ÷ 周期额度 × 用量比例） |
| 预算掐死探索 | 不敢用 AI 做发散尝试 | 探索池独立、月底清零、不占生产额度 |
| 变成焦虑源 | 每天盯红色数字，两周后弃用 | 收益框架主视觉、周维度看趋势、溢出不惩罚 |
| 用户开始骗系统 | 换工具绕开、手动改数 | 计量自动化；绕开行为在周报里提示但不指责 |
| 资讯噪音反噬 | 推得多、看得少 | 长度硬约束、空报告合法、命中率反馈 |
| 隐私顾虑 | 担心账本被上传 | 本地优先、开源、可审计、默认零上传 |
| 宿主能力不足 | 拿不到逐请求用量或无法拦截工具 | M0 先验证，降级路径提前设计 |

## 12. 验收标准

- **AC-1** 给定日预算 10 元、已完成 2/3 交付项，当花费达到 10 元时，系统立即进入 LOCKED，禁止发起任何新任务，生成溢出报告，并将剩余 1 项顺延至次日队首。
- **AC-2** 二级上限未启用时，界面**不存在**任何"继续工作"的入口（收尾豁免除外）。
- **AC-3** 当启用条件不满足时，"申请二级上限"按钮置灰，并明确显示缺少哪个条件。
- **AC-4** 给定 3 个任务共 22 元预估、日预算 10 元，排期输出 P50 = 第 3 个工作日、P80 = 第 4 个工作日；若期望日期为第 2 日，标记不可行并展示三个杠杆。
- **AC-5** 当顺延工作量 > 2 个标准日时，开工前强制展示"重谈"对话，未处理则次日再次展示。
- **AC-6** 给定关注源今日无 P0 事件，简报输出"今天没有值得你花时间的事"，条数为 0，不产生通知。
- **AC-7** 断网状态下，计量、硬顶、排期、溢出报告全部正常；简报显示"稍后重试"且不丢事件。
- **AC-8** 收尾豁免额度 0.5 元内允许提交与测试；超出后仅允许零 token 本地操作，且不产生新的模型请求。
- **AC-9** 月度内第 3 次启用二级上限时，启用前强制展示本月启用次数与"排期可能偏乐观"提示。
- **AC-10** 卸载插件后无残留进程与定时任务，历史账本保留在用户数据目录。

## 14. 待确认问题

1. **宿主范围**：默认按 DSH 插件设计（面板 + 工具拦截 + 会话数据）。是否还要覆盖 DSH 之外的 Claude Code / Codex CLI？若需要，M8 的本地代理方案是否接受？
2. **计费构成**：主要用哪几家、各自按量还是订阅？直接决定元当量的折算复杂度。
3. **二级上限参数**：20 元是否固定？每月 4 次配额是否合适？是"当天临时开"还是"至少提前一天申请"？（提前申请更接近排期行为，临时开更接近情绪行为）
4. **承诺日谁定**：你单方面定，还是要和上级/客户对齐？如果要对齐，溢出报告是否需要"对外话术"模板？
5. **结余处理**：是否同意"不结转成钱、只兑换成时间"？1 元 = 48 分钟（10 元 ≈ 8 小时）是否接近你的实际节奏？
6. **积压阈值**：2 个标准日触发"强制重谈"是否太紧或太松？
7. **个人账本产出物**：自媒体具体形态（视频 / 图文 / 代码项目）？要不要记录发布数据？
8. **资讯渠道**：中英混排还是中文优先？X 上的信息是否必须（涉及登录与抓取可行性）？
